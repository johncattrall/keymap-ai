# Keymap diagrams and repo tooling (keymap-drawer)

Works for both ZMK (`keymap parse -z config/<kb>.keymap`) and QMK (`keymap parse -q` on `qmk c2json` output or `-c` on via/keymap.json). Goal: per-layer SVGs embedded in the README, regenerated by CI, readable in light and dark mode.

## Drawer config (keymap_drawer.config.yaml)

- `parse_config.zmk_keycode_map`: map verbose keycodes to glyphs; use platform-appropriate modifier symbols (⌘⌥⌃⇧ on macOS, Ctl/Alt/Win elsewhere).
- `parse_config.raw_binding_map`: label custom behaviors (`"&td_num": {t: NumWord, s: 2x Lock}`) and parameterized user behaviors/macros; autoshift-style wrappers get per-key entries with `s:` shifted legends.
- `draw_config.dark_mode: auto` + NO background color = transparent SVGs that adapt via prefers-color-scheme. Custom colors only on elements that carry their own background, with outlined text (`paint-order: stroke`).
- Do NOT set `n_columns` when generating per-layer images (pitfall 12).
- Give every keymap layer a `display-name`; the drawer and ZMK Studio both use it.

## Per-layer output

`keymap draw <parsed>.yaml -s <LayerName>` draws one layer. Loop over layer names from the parsed YAML; slugify for filenames (`crosses_nav-num.svg`).

## Virtual keys for trackballs and encoders

Physical layouts only know keys, so add hardware as extra layout entries plus per-layer label injection:

1. Generate a drawing-only layout JSON from the real one, appending positioned entries (e.g. `{"x": 5.02, "y": 2.25, "w": 1.4, "h": 1.4}` per ball). Never modify the firmware's own layout file.
2. Keep a checked-in `trackballs.yaml`: `default:` pair plus per-layer overrides, each entry a drawer key spec with `type: trackball`.
3. After parsing, append the per-layer entries to each layer's key list, then draw with the augmented layout.
4. Style via `type`-derived classes: `rect.trackball { rx/ry for roundness; fill; }` with `.side` variant for depth, and outlined white text. A red ball matching the hardware reads instantly.

## Diff visualization

To show an audit change visually, render before/after images and give changed keys `type: added` (or `removed`) in the drawer YAML, with self-colored CSS (`rect.added { fill: #2f7d46; }` plus white outlined text) so it reads in both themes. Green additions on an otherwise plain board communicate a finding faster than prose.

## Full-width GitHub rendering

GitHub clamps images with `max-width: 100%` but renders dimensionless SVGs tiny. Post-process: double the declared width/height attributes (keep viewBox); images then render at exactly full column width, crisp.

## CI: one workflow, two jobs

Merge drawing into the existing build workflow (two workflows per push reads as noise):

- Job `build`: the firmware reusable workflow (ZMK: `zmkfirmware/zmk/.github/workflows/build-user-config.yml@<release>`).
- Job `draw` (skip on pull_request): pipx install keymap-drawer; parse, augment, draw per layer + combined; dimension post-processing; commit with `[skip ci]`; `git pull --rebase` before push to survive concurrent runs.

Users must know: the bot commit puts the remote ahead, so `git pull --rebase` before local work.

## README structure that works

Photo (web-optimized: ~1600px, ~80% JPEG, EXIF stripped, committed under `images/`), keymap section with each layer under its own heading plus a link to the combined image, features list, layer purpose table, hardware table, pointing-device roles table, module tree with credits, build/flash instructions including a settings_reset artifact, and a note that the keymap file is the source of truth over ZMK Studio.
